# Synchronization

Each account has one in-process `Mutex`; sync, manual older-mail loading, and account removal run sequentially for that account. WorkManager uses a unique one-time work name per account, with `KEEP`, network connectivity constraints, and exponential backoff. Existing accounts are queued once at application startup; a successful account setup schedules 24-hour periodic work. Account removal cancels both work names before removing local account data and its encrypted credential. Periodic work is opportunistic rather than exact.

The initial Inbox metadata pass fetches the newest **50 messages by sequence number**, rather than walking history from UID 1:

```text
CAPABILITY → LOGIN → CAPABILITY → LIST → SELECT INBOX → FETCH newest sequence window
```

Its checkpoint is set to `UIDNEXT - 1`. Subsequent syncs request `UID FETCH checkpoint+1:checkpoint+200`, bounded by the selected Inbox's `UIDNEXT - 1`. These are UID ranges, so sparse ranges may contain fewer than 200 messages or none. The checkpoint advances to the requested range boundary even when no message is returned. A successful page with more new UIDs is continued by WorkManager retry/backoff. Automatic sync does not enumerate older history.

Fetched metadata is parsed before a Room transaction starts. It is committed in batches of at most 200 messages. Each normal metadata batch writes canonical messages, mailbox membership, flags, labels, and the checkpoint together; a failed transaction cannot advance the checkpoint. The checkpoint records mailbox, account, `UIDVALIDITY`, highest known UID, generation, and final-success time.

On a `UIDVALIDITY` change (the recovery behavior introduced in e731423), GlassMail clears Inbox memberships, deletes the obsolete checkpoint, and nulls captured target UIDs on active account mutations in one transaction. The old incremental response is discarded, and the newest 50 messages are fetched again. The stored mailbox validity also detects a reset when the checkpoint is absent. Canonical messages remain; Gmail messages reuse their `X-GM-MSGID` identity. The reset does not increment the old checkpoint generation: the replacement checkpoint starts at the default generation. Mutation execution checks the selected server validity against the checkpoint and defers mismatches; archive undo cannot restore a captured UID invalidated by recovery.

After new-mail persistence, every successful sync reconciles **cached Inbox memberships** within the cached UID window, through `highestKnownUid`. It requests the actual cached UIDs in commands covering at most 500 UIDs: `UID FETCH <UID set> (FLAGS X-GM-LABELS)`. This pass fetches no bodies or envelopes. Responses replace cached flags and label rows; Gmail category labels also update the category when present. A cached UID absent from the selected server Inbox has its Inbox membership removed, reflecting remote archive, trash, or deletion. Reconciliation neither discovers older uncached messages nor repairs uncached gaps below the checkpoint.

Reconciliation applies each chunk in one cancellable Room transaction, checking current membership and active mutations again after the network read. Messages with active `PENDING` or `IN_FLIGHT` mutations are skipped entirely, including membership removal. Reconciliation runs **before** mutation flushing, so acknowledgement cannot expose a pending message to a response fetched before its intent was sent. Normal metadata persistence overlays pending read/unread, star/unstar, and label additions/removals, and never recreates membership for a pending archive or delete. This also allows pending flag/label actions to acquire fresh UIDs after namespace recovery.

Local actions are applied in one Room transaction with a `PendingMutationEntity`. Successful server acknowledgement deletes the record. Transient transport errors return mutations to `PENDING` with an incremented retry count. Authentication and protocol/server-rejection errors become `FAILED_PERMANENT`; these records are not active intent. Cancellation is rethrown. Archive and delete remove local membership immediately; archive stores the captured UID and previous membership for undo.

The Inbox footer provides **Load older mail**, with transient per-account loading, retry, exhausted, and cache-limit states, including in the unified Inbox. Each manual request uses `UID SEARCH UID 1:(lowest cached Inbox UID - 1)` and fetches metadata for the last up to 50 matching UIDs. Sparse UIDs are handled by searching actual messages. UID 1 or an empty older search means exhausted. The page is limited to the remaining capacity of the account's configured cached-message preset; loading stops when the cached Inbox membership count reaches that cap. Existing cache enforcement still runs after persistence. New automatic mail may take the membership count above the preset; cache enforcement continues its existing body/attachment eviction behavior rather than deleting Inbox metadata.

Older-mail persistence writes messages, memberships, and labels in one transaction without changing the sync checkpoint, its timestamp, or the notification baseline. It checks server `UIDVALIDITY` before fetching; a mismatch discards the older request and invokes normal namespace recovery. Users can retry after sync. Reconciliation and manual backfill do not post new-mail notifications. Initial sync establishes a notification baseline without notifying; later new-mail pages retain the existing notification behavior.

Detached canonical messages and attachments are deliberately retained, including FTS content, to preserve draft references, mutation references, and possible later reuse of Gmail identities. Their labels are rebuilt from remaining memberships (cleared if none remain). Inbox and current search queries join mailbox memberships, so detached messages do not appear there. This is not a garbage-collection pass.

Metadata fetches include envelope, selected list/category headers, flags, labels, and Gmail identifiers when supported. Sync additionally prefetches up to 12 returned unread bodies when enabled, refreshes quota, enforces body/attachment cache limits, and syncs remote drafts after the final new-mail page. Reader bodies and attachment bytes are also available on demand. Live end-to-end Gmail validation remains unverified.
